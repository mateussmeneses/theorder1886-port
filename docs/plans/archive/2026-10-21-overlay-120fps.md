# Expose the existing 120 FPS patch in the in-game menu

Issue: https://github.com/mateussmeneses/theorder1886-port/issues/22

## Evidence and scope

The launcher already offers 120 game FPS (`engine_fps=240`), startup maps that
setting to `Frame Rate Patch - 120 FPS`, and the built-in XML includes the patch.
The in-game Performance tab still offers only 30 and 60 FPS, although its
`PortGraphics::EngineFps` values already contain 60, 120, and 240. The engine's
value is twice the displayed game frame rate.

History explains the mismatch: `d36f8f4` limited the overlay when only the 60 FPS
patch was verified; `1d09fa0` subsequently added the 120 FPS patch and launcher
choice without updating the overlay row.

This change exposes an existing experimental option. It does not add an
upscaler, validate FSR 4.1.1, promise stable 120 FPS, or change the patch bytes.

## Implementation

1. Add a third engine-frame-rate label, `120 (experimental)`, mapped to the
   existing value 240. Keep the original options, order, and default.
2. Derive the row count from the existing value array instead of hardcoding two.
   Report applied/requested frame rates dynamically when a requested patch is
   unavailable, including a 120 FPS request falling back to 60 FPS.
3. Confirm the selected value persists through settings save/load, triggers the
   restart requirement, resolves to the existing 120 FPS patch, and gives an
   effective limit of 120 game FPS after that patch is applied.
4. Run applicable tests, attempt the repository gate, and obtain an independent
   review before opening a separate PR against `master` referencing #22.

## Acceptance

The Performance tab can select all three supported engine values with labels in
game FPS. Settings, patch selection, and frame-limit arithmetic agree on 120
FPS. Keep source inspection and standalone backend checks distinct from an
interactive overlay/gameplay test.

## Validation results

- A temporary native harness compiled the exact `PerformanceTab`, `Choice`, and
  `Store` functions with UI doubles and the real settings implementation. The
  original source failed because its combo had only two choices; the changed
  source passed for all three labels and values. Save/reload, restart detection,
  the unchanged default, and the effective 120 FPS limit passed.
- This harness verifies the row call and backend behavior; it does not render
  ImGui, simulate actual keyboard/controller input, or run the game.
- Startup mapping selects the existing 120 FPS patch for `engine_fps=240`.
  Compiling its reference addresses produces four writes of 8333 microseconds;
  applying those writes to a real game executable remains untested here.
- Focused Python checks passed: graphics options 8, launcher controls 25, and
  patches 17 (15 passed, 2 skipped because no prepared eboot is available).
- The full gate is blocked by missing Ninja. A full overlay build and interactive
  gameplay/pacing test remain pending.
- Full Python discovery: 292 tests, 214 passed, 76 skipped, and the same two
  existing errors caused by missing `tkinter` in `test_launcher_game_files`.
- Independent review identified a related hardcoded fallback message: a 120 FPS
  request falling back to 60 FPS would incorrectly report 30 FPS and a missing
  60 FPS patch. The message now derives both rates. The native harness passed
  for 120-to-60, 120-to-30, 60-to-30 fallbacks and no warning when 120 FPS applies.
  Final GPT-6.1 Sol review found no remaining actionable issues and independently
  reran the expanded harness successfully. `git diff --check` passed.
